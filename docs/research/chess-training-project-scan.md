# Chess training project scan

Status: **research and recommendations only; not product decisions**. Reviewed 2026-10-16 from public project pages, repositories, and documentation. Feature descriptions below are attributed summaries, not endorsements or claims of comparative effectiveness. Some names are ambiguous; those cases are called out rather than silently conflated.

## Cross-cutting takeaways

1. **Keep learning modes distinct.** Scheduled recall (ChessReps core), fixed-set cycles (ChessPecker/Disco), speed (Blitz Tactics/ChessCup), opening discovery/repertoire (ChessRoots/Chessbook), visualization (Listudy/ChessMemory), and move ranking (Chessort) measure different things. Avoid folding them into one opaque score or scheduler.
2. **Opening repertoire is the strongest adjacent product area.** Chessbook's move-level SRS suggests a meaningful extension: a repertoire tree with position-level prompts and per-decision review state. This needs a separate product/task design and export/migration review, not an unapproved schema change.
3. **Near-term ideas with modest dependencies:** expose the immediately preceding setup move in puzzle context; richer filters over existing tags/opening metadata; optional fixed-set cycle mode; a separate timed sprint mode. These are recommendations only and should be prioritized through the backlog.
4. **Personal game-derived training is compelling but gated.** Disco Chess-style missed-tactic review would require game import, analysis provenance, privacy controls, and clear data ownership.
5. **Offline-first remains a differentiator.** Bundled content and durable local progress are shared by offline tools, but the product should not inherit assumptions about accounts, live APIs, or cloud leaderboards.

### User-identified Blitz Tactics pattern

The user is currently trying Blitz Tactics and specifically finds its **difficulty-graded sets with speed-and-mistake-based unlocks** interesting. This is more than a generic timed mode: it provides a visible progression ladder and mastery gate. A ChessReps adaptation could use curated/filtered sets, require both an accuracy threshold and a time target to unlock the next tier, and allow replay of prior tiers. Recommendation: make this a separate optional mode, not a change to scheduler grading or due dates. Before design, decide whether time targets are per-puzzle or whole-set, how hints count, and whether unlocks are durable/exported user progress.

### User-identified Woodpecker pattern

The user also likes the Disco Chess workflow: train a fixed set of about **500 puzzles** in repeated Woodpecker-style cycles, while puzzles missed in a cycle are routed into a separate **spaced-repetition failed-puzzle section**. This combines two goals: complete the fixed set faster/more accurately over successive passes, and revisit individual misses on their own due schedule. Treat this as a confirmed product preference for future F01 design, not an implementation/schema decision. Keep cycle membership and pass-completion metrics distinct from the normal scheduler; define how misses enter/rejoin maintenance, whether corrections count as cycle completion, and how set size affects targets before building it.

## Scope update: puzzle context

User preference updated on 2026-10-16: **for now, show only the immediately preceding move** (the puzzle setup move), not the full source game. The existing puzzle content already stores `setupMove` and the source FEN; a UI treatment can likely display that move as context without adding full-game data. Confirm exact presentation against the current board/move-list behavior before implementation. Full-game context is deferred, not rejected permanently. This narrows PZL-002 and avoids the unresolved monthly archive join for the immediate feature.
